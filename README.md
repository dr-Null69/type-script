# Лабораторна робота №7: Performance and Load Testing
**Тема:** Навантажувальне тестування REST API сервісу оренди обладнання (SUT B, Варіант 12)  
**Інструменти тестування:** **Grafana k6** + **Apache JMeter** (максимальний бал — 7)

---

## 1. Мета роботи
Навчитися будувати сценарії навантажувального тестування REST API з динамічною передачею даних між пов'язаними HTTP-запитами, проводити базове (baseline), робоче (load) та пікове (stress) тестування, аналізувати показники швидкодії (Avg, p95, Throughput, Error Rate) та порівнювати особливості роботи різних інструментів.

---

## 2. Тестований сценарій (Dynamic Data)
У тесті реалізовано бізнес-сценарій клієнтської сесії, що складається з двох послідовних запитів:
1. **Запит 1 (POST `/rentals`):** Створення нової заявки на оренду обладнання. Кожен запит генерує унікальний ідентифікатор `reference` (UUID), щоб уникнути колізій у базі даних.
2. **Екстракція динамічних даних:**
   * У **k6**: через `postRes.json().id`.
   * У **JMeter**: через елемент `JSON PostProcessor` з виразом `$.id` у змінну `${RENTAL_ID}`.
3. **Запит 2 (GET `/rentals/${id}`):** Отримання деталей щойно створеної оренди за отриманим ідентифікатором.
4. **Think Time:** пауза 100 мс між ітераціями для імітації реальної поведінки користувача.

### Критерії прийнятності (Thresholds / SLAs)
* `http_req_duration`: **p95 < 500 ms** (95% запитів мають оброблятися швидше за пів секунди).
* `http_req_failed`: **Error Rate < 1%** (частка невдалих відповідей не більше 1%).

## 5. Інтерпретація метрик та поведінки системи

1. **Baseline Test (контрольний стан):**
   * При мінімальному навантаженні (1 користувач) сервіс демонструє стабільно низький час відгуку (**5–10 мс**), відсутність черг і нульовий відсоток помилок (**0%**). Критерії SLA повністю виконано.
2. **Load Test (робоче навантаження 15 VUs):**
   * Пропускна здатність системи масштабувалася пропорційно до **~110 req/s** в обох інструментах (110.3 у k6 та 109.2 у JMeter).
   * Однак спостерігається сплеск помилок (~41–48%). **Причина:** у сервісі використовується одне глобальне синхронне з'єднання з базою даних (`app.state.conn`) без пулу з'єднань (Connection Pool). Одночасні транзакції `POST /rentals` створюють колізії сесій PostgreSQL.
3. **Stress Test (пікове навантаження 60 VUs):**
   * Зафіксовано досягнення точки відмови (Breaking Point).
   * Час відгуку p95 зріс до **193–415 мс**.
   * З'явилися мережеві помилки `wsarecv: An existing connection was forcibly closed by the remote host`, викликані переповненням черги вхідних TCP-з'єднань сокетів сервера та вичерпанням робочих потоків.

## 6. Порівняння інструментів (k6 vs Apache JMeter)

| Критерій | Grafana k6 | Apache JMeter |
| :--- | :--- | :--- |
| **Архітектура / Мова** | Go (компілюється в нативний бінарник), скрипти на JavaScript. | Java (JVM), сценарії конфігуруються у GUI/XML (`.jmx`). |
| **Модель потоків (Concurrency)** | **Event Loop + Goroutines (Go)**: неблокуючий ввід/вивід. Один потік ОС може обслуговувати тисячі віртуальних користувачів. | **Thread-per-VU**: кожен віртуальний користувач — це окремий потік операційної системи (Java Thread). |
| **Споживання ресурсів** | Дуже низьке споживання RAM і CPU на машині тестувальника. | Значно вище споживання оперативної пам'яті (JVM heap) та навантаження на планувальник ОС. |
| **Зручність автоматизації (CI/CD)** | Ідеально підходить для Git/CI (код як тести `Tests-as-Code`, легкий запуск у контейнерах). | Потребує середовища Java; традиційно використовується у великих enterprise-системах. |
| **Результати пропускної здатності** | Продемонстрував високу точність фіксації мікросекундних мережевих затримок і практично однаковий throughput з JMeter (~110 RPS у Load-тесті). | Продемонстрував високу продуктивність генерації запитів у CLI режимі (`-n`), детальний HTML Dashboard. |

## 7. Висновки
* Побудовано і протестовано навантажувальний ланцюжок із двох залежних запитів з коректним динамічним вилученням `id` сутності.
* Проведено комплексне дослідження (Baseline, Load, Stress) на двох різних інструментах (k6 та JMeter), отримано практично ідентичні результати щодо пропускної здатності (~110 RPS у Load) та межі стійкості сервісу.
* Виявлено вузьке місце тестованого сервісу — відсутність пулу з'єднань до бази даних (Database Connection Pooling), що призводить до відхилення запитів при конкурентних транзакціях вище 10–15 користувачів.
